# Agent Note：应用凭据属于卡片，密钥不属于

Status: implemented

[English](2026-09-13-social-application-credentials-in-settings.md) | 中文

## 问题

社交提供方只能通过部署的环境变量被告知使用哪个应用登录。改正一个粘贴错的 client id 意味着编辑环境变量并重新部署，而产品里没有任何地方说明这个值该放在哪。操作者提出了显而易见的问题：为什么这没有界面？

当时并没有一个站得住脚的答案。代码里的理由——"设置里的密钥就是配置界面里的密钥"——对密钥而言是成立的，但三个提供方把它推广到了所有应用层面的值。与此同时，harness 在别处并不坚持这条线：`cloudflare` 直接接受 `apiToken`，并在自己的 schema 描述里写明了这个取舍；`social-youtube` 也早就接受内联的 `clientId` 和 `clientSecret`。三个社交提供方里只有 LinkedIn 和 Meta 是纯引用式的，而这三个包是并行写出来的——这才是真正的原因。

还有一个本可以一锤定音的论据——智能体能改设置但不能改环境变量——同样不成立：没有任何工具会写设置。

## 决定

把"凭据"这个词拆开，两半区别对待。

**应用凭据**——client id、app id、回调地址、Instagram 的公开媒体基地址——属于配置。每个提供方现在提供一个以自己命名的设置命名空间（`social-linkedin`、`social-meta`、`social-youtube`），社交卡片为每个应用提供一个表单。

**账号凭据**——发布时所用的令牌——保持不变：通过授权 seam 获取，通过凭据 seam 存储，永远不进表单。

**应用密钥处在两者之间，且两条路都不走。** 它不是设置字段。写进设置段的密钥会随该段的每一次读取回到浏览器并留在表单里；取而代之，每个段只记录密钥所在的环境变量或凭据记录的名称，而卡片通过凭据域写入密钥——凭据域只报告是否已配置，永不交回。`SecretField` 与 `CardSecretSpec` 正是为此而存在（web-search 卡片的 API key），所以卡片复用它们，而不是再造一个答案。

优先级在注册包的 `resolveAppCredential` 里一次性固定：设置、组合配置、被命名的环境变量，且每一层的空白都视为缺失。设置优先，因为那是一个人无需重新部署就能改动的层；一个填进表单却被忽略的值，比从未提供的表单更糟。

### 这带来的连锁改动

Meta 此前在 `apply` 时就捕获了 `redirectUri` 和 `publicMediaBaseUrl`。改为惰性读取，因为需要重启才生效的"保存"是在撒谎。

使用 `ctx.inject(['settings'], …)` 而非 `ctx.get('settings')`，理由记录在[设置命名空间那篇](2026-09-13-social-settings-namespace-await.md)：该服务在与之一同组合的插件 apply 之后才解析。`settings` 仍不进 `inject`——没有它的组合保留工具，只失去表单。

表单机制（`CardForm`、`textField`、`ValueField`、`SecretField`）现从 `ui-settings-plugins` 导出。`PluginCard` 刻意不导出：它的 props 是该包自有字典的 locale key，外部卡片无法用它给自己起标题。

`tsconfig.base.json` 增加了十条手写路径别名。对于 npm 名称带有目录所没有的 `client-`/`host-` 前缀的包，`gen-tsconfig-paths` 无法推导别名，所以自那些包落地以来它一直在失败——而没有别名，对这类包的运行时导入会经 `node_modules` 解析到其构建产物 `lib/`。社交包的第一次跨包运行时导入暴露了这一点：测试当时跑的是过时的 bundle。

## 考虑过的替代方案

**用一个 `social` 命名空间装下所有提供方的凭据。** 一张卡片、一个命名空间，不必为每个提供方 `settingsScope.bind`。否决：那样 `tool-social` 将持有提供方专属字段，第四个提供方不改消费者就无法加入自己的字段。

**像 `cloudflare` 对待其 token 那样，把密钥放进设置。** 改动最小，也是先例所指向的做法。否决：做得更好的机制已经存在，代价只是多一个字段；只写不读的控件严格优于把密钥渲染回表单，而"与较弱的先例保持一致"不构成复制它的理由。

**从 `/social/status` 发现这些区块，而不是静态列出。** 那样提供方无需改动卡片即可加入，但在渲染期为每个提供方绑定设置作用域与插槽架构相冲突——注入面是在注册时构建的。`ui-settings-plugins` 静态列出它的七张卡片；这里静态列出三个。

## 后果

- 应用凭据在浏览器里设置和改正，并在下一次操作时生效，而不是下一次部署。`DSH_SOCIAL=1` 仍然只能由环境变量设置：它决定是否存在这张卡片。
- 密钥可以被替换，但永远无法被读出。即使已经设置，输入框也是空的；而空白意味着"保留现有的"——这一点必须写进文案，否则空白会被读成"未设置"。
- 表单报告的是*已存储*什么，从不报告某个值*能用*。要证明 id 与密钥匹配，必须发起一次登录。
- 装载了提供方却没有设置服务的部署不会看到表单，也不会有任何说明。它仍可使用环境变量，所以这是一条记录在案的限制而非缺陷。

# Agent Note：标签页重新回到视野，就是一个重连信号

Status: implemented

[English](2026-09-16-reconnect-on-tab-return.md) | 中文

## 问题

操作者让 Web GUI 开着，去做别的事，回来时看到一个 `disconnected` 标记。发送消息看起来毫无反应——但消息其实已被接收并处理。手动刷新页面后，连接显示正常，而答复早已在那里等着。

`ConnectionController` 会带退避地永远重试，`watchBrowserNetwork` 又把 `online`/`offline` 喂给它，纸面上这应当能自愈。事实并非如此，因为这两个事件都没有描述真正发生的事：网络从未中断，是**标签页**睡着了。隐藏的标签页其定时器会被钳制，在后台几分钟后更会被彻底冻结，于是那个本该替换掉死连接的重试并不是迟到——它是停住了，而且没有任何东西被安排来重新启动它。

发送在整个过程中依然有效，因为它走 HTTP，与事件流相互独立。消失的只是那条本该把答复呈现出来的通道——这也正是为什么页面一被重建，答复就已经在那里。

## 决定

`watchPageVisibility` 在页面重新回到视野时重连：

- **`visibilitychange`** 变为可见——切回标签页这一普通情形。
- **`pageshow`**——这是前进/后退缓存恢复唯一会触发的信号。那种页面是完全冻结着恢复的，带着一个死掉的连接，并且根本不会有任何可见性转换。

它调用既有的 `ConnectionController.reconnect()`，后者本就会重置尝试计数并中止待定的延迟；因此恢复本身无需发明任何新东西——需要新增的只是"察觉到此时该恢复了"。

**以"当前未连接"为前提。** 一个切走一秒又切回来的标签页，其连接完好无损；替换它只会白白花掉一个连接世代。

## 考虑过的替代方案

**调小 `backoffMaxMs`，让冻结的标签页更快自行恢复。** 行不通：问题不在于等待多久，而在于定时器根本没在走。而且这会让真正不可达的 Host 永远处于更激进的重试，而 10 秒上限正是为那种情况存在的。

**按间隔发心跳，漏拍就重连。** 同样的缺陷——间隔也是定时器，会和其他一切一起被冻结。它还会给每一个空闲会话增加流量，去检测一个浏览器本来就免费告知的状态。

**每次可见性变化都重连。** 少一个判断条件，但是错的：大多数返回面对的是健康连接，而每一次多余的重连都要花掉一个世代，并带来一次可见的 `connecting` 闪烁。

## 后果

- 回到睡着的标签页无需手动刷新即可恢复。
- 对于 JavaScript 本身已被驱逐的页面，刷新仍是唯一的恢复方式；本改动针对的是"页面还活着但连接已死"，也就是被报告的那种情形。
- 该监听器只在 `window` 与 `document` 同时存在时才挂载，因此在 node 测试环境以及任何非浏览器嵌入中都是惰性的。
